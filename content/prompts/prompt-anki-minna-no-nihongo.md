# Универсальный промпт для создания Anki-колод Minna no Nihongo

Создай готовую отдельную Anki-колоду с лексикой учебника **「みんなの日本語 初級Ⅰ / 初級Ⅱ」**.

## 1. Параметры

* Номер урока: `{LESSON_NUMBER}`
* Учебник: Minna no Nihongo.
* Язык переводов и объяснений: русский.
* Формат результата: `.apkg`.
* Название файла: `Japanese_Lesson_{LESSON_NUMBER}.apkg`.

**Главное требование:** все колоды независимо от номера урока должны иметь одинаковую структуру, оформление, схему именования и формат Anki. Меняется только номер урока и учебное содержимое.

Не объединяй колоды разных уроков и не изменяй ранее созданные колоды.

---

## 2. Единый стандарт именования

Используй следующую схему во всех будущих колодах.

**Имя файла:**

`Japanese_Lesson_{LESSON_NUMBER}.apkg`

**Внутреннее имя колоды в Anki:**

`Japanese Lesson {LESSON_NUMBER} - Minna no Nihongo`

**Название типа заметок:**

`Minna no Nihongo · Vocabulary · two directions`

Примеры:

| Урок | Имя файла               | Имя колоды в Anki                     |
| ---- | ----------------------- | ------------------------------------- |
| 10   | Japanese_Lesson_10.apkg | Japanese Lesson 10 - Minna no Nihongo |
| 11   | Japanese_Lesson_11.apkg | Japanese Lesson 11 - Minna no Nihongo |
| 12   | Japanese_Lesson_12.apkg | Japanese Lesson 12 - Minna no Nihongo |

Правила:

* Не добавляй к имени файла `_fixed`, `_repaired`, `_final`, `_v2` и другие суффиксы.
* Не добавляй произвольные подколоды.
* Не изменяй название типа заметок между уроками.
* Каждая колода должна иметь собственный идентификатор колоды.
* Одинаковые по структуре типы заметок должны сохранять совместимую идентичность.
* Не используй одинаковые идентификаторы заметок и карточек для разных уроков.
* Не допускай, чтобы импорт одного урока перезаписывал карточки другого.

Если файл приходится исправлять, исправляй его содержимое и создавай итоговый файл с тем же стандартным именем.

---

## 3. Эталон оформления

Если приложен файл `Japanese_Lesson_10_repaired.apkg`, используй его как основной эталон.

Извлеки из него:

1. Тип заметок.
2. Структуру и порядок полей.
3. HTML лицевой стороны обеих карточек.
4. HTML обратной стороны обеих карточек.
5. Полный CSS.
6. Размеры текста, отступы, цвета и визуальную иерархию.
7. Способ отображения фуриганы.
8. Расположение меток частей речи.
9. Расположение примеров и блока «Употребление».

**Не изменяй оформление без отдельной просьбы.**

Используй предыдущую колоду исключительно как образец оформления и технической структуры. Не переносите её слова и карточки в новую колоду.

Если эталон не приложен, используй приведённую ниже каноническую спецификацию.

### Структура полей

Порядок полей должен оставаться неизменным:

| № | Поле           | Назначение                         |
| - | -------------- | ---------------------------------- |
| 1 | Japanese       | Японское слово без фуриганы        |
| 2 | Russian        | Русский перевод                    |
| 3 | PartOfSpeech   | Часть речи или тип прилагательного |
| 4 | Example        | Пример без фуриганы                |
| 5 | ExampleRussian | Русский перевод примера            |
| 6 | Usage          | Краткая подсказка по употреблению  |
| 7 | JapaneseRuby   | Слово с HTML ruby                  |
| 8 | ExampleRuby    | Пример с HTML ruby                 |

Не переименовывай поля и не изменяй их порядок.

### Визуальный стандарт

* Белый фон.
* Тёмный основной текст.
* Крупное японское слово — 36 px.
* Русский перевод — 25 px.
* Пример — 23 px.
* Фуригана — приблизительно 48% размера основного текста.
* Небольшая сдержанная метка части речи.
* Пример, перевод и употребление отделены от основного слова тонкой линией.
* Текст японских слов расположен по центру.
* Примеры и объяснения выровнены по левому краю.
* Адаптация размера японского текста для мобильных устройств.

Если эталон доступен, его исходный CSS имеет приоритет перед этим описанием. Не пытайся воссоздавать CSS приблизительно — копируй его точно.

## 4. Содержание урока

Определи стандартную лексику Minna no Nihongo для урока `{LESSON_NUMBER}`.

Включи:

* существительные;
* глаголы;
* прилагательные;
* наречия;
* вопросительные слова;
* устойчивые выражения;
* разговорные фразы;
* служебные слова, если они входят в словарь урока.

Ориентируйся на стандартный словарь распространённого издания учебника.

Не добавляй слова других уроков ради увеличения количества карточек.

Не устанавливай искусственное количество слов.

Если для определения точного состава словаря требуется внешний источник, проверь его до начала создания колоды.

---

## 5. Формат карточек

Одна заметка должна создавать строго две карточки.

### Карточка 1 — Японский → русский

Лицевая сторона:

* Японское слово с фуриганой.
* Отдельная метка части речи, если она полезна.

Обратная сторона:

* Содержимое лицевой стороны.
* Русский перевод.
* Японский пример с фуриганой.
* Русский перевод примера.
* Блок «Употребление».

### Карточка 2 — Русский → японский

Лицевая сторона:

* Русский перевод.

Обратная сторона:

* Японское слово с фуриганой.
* Метка части речи, если нужна.
* Японский пример с фуриганой.
* Русский перевод примера.
* Блок «Употребление».

Не создавай дополнительные типы карточек.

Не оставляй пустыми поля Japanese, Russian, Example, ExampleRussian, JapaneseRuby и ExampleRuby.

Поле Usage должно содержать краткую полезную подсказку.

PartOfSpeech может оставаться пустым, если метка не нужна.

---

## 6. Фуригана

Используй правильные чтения кандзи.

При подготовке учебных данных допустим формат:

`漢字[かんじ]`

Однако поле `JapaneseRuby` должно содержать корректную HTML-разметку:

```html
<ruby>漢字<rt>かんじ</rt></ruby>
```

Это важно: не вставляй текст `漢字[かんじ]` в обычный HTML-шаблон без обработки. Anki не обязан автоматически преобразовывать его в фуригану.

Для отображения используй поля `JapaneseRuby` и `ExampleRuby`.

Пример:

```html
<ruby>静<rt>しず</rt></ruby>か
```

Не добавляй фуригану над хираганой или катаканой.

Не помещай грамматические признаки внутрь фуриганы.

Неправильно:

`静[しず]か[な]`

Правильно:

`静[しず]か`

Тип прилагательного должен находиться отдельно.

---

## 7. Прилагательные

Для прилагательных указывай тип в поле `PartOfSpeech`:

`い-прилагательное`

или

`な-прилагательное`

Не помещай эту информацию в JapaneseRuby.

Не добавляй `な` к словарной форме な-прилагательного только ради обозначения типа.

В примерах используй окончания и частицы согласно изученной грамматике.

---

## 8. Глаголы

Сохраняй словарную форму представления глагола, принятую в словаре соответствующего урока Minna no Nihongo.

Если учебник приводит глагол в форме `～ます`, используй именно эту форму как основную.

Не заменяй её автоматически на простую словарную форму из более поздних уроков.

В блоке Usage можно указать типичную конструкцию:

`～が 分[わ]かります`

`～を 見[み]ます`

`～に あります`

Объяснение должно быть кратким и практическим.

---

## 9. Учебные примеры

Для каждого слова составь короткое естественное предложение.

**Строго соблюдай ограничение грамматики уроками 1–{LESSON_NUMBER}.**

Для урока 10 нельзя использовать грамматические конструкции, впервые изучаемые в уроках 11 и далее.

Проверяй:

* формы глаголов;
* времена;
* частицы;
* формы прилагательных;
* отрицания;
* порядок слов;
* грамматические конструкции.

Не используй грамматику следующих уроков даже в том случае, если она делает предложение естественнее.

Примеры должны содержать преимущественно уже знакомую лексику.

Не делай предложения сложными только ради демонстрации слова.

---

## 10. Русский перевод и употребление

Переводы должны быть естественными и понятными начинающему.

Если слово имеет несколько основных значений, укажи их через запятую или точку с запятой.

Не добавляй редкие значения, которые не нужны на текущем уровне.

Блок Usage должен содержать краткую подсказку, обычно 1–3 строки.

Пример:

**Употребление:** `～が 好[す]きです` — нравится что-либо.

Не превращай карточку в подробный урок грамматики.

# 11. КРИТИЧЕСКИ ВАЖНО: правильное создание APKG

Этот раздел обязателен.

Ранее созданные колоды вызывали ошибки:

```text
500: JsonError { info: "decoding decks: JsonError" }
```

и

```text
500: DbError {
  info: "no such table: graves"
}
```

Новая колода не должна содержать подобных структурных ошибок.

### Используй надёжный механизм экспорта

Предпочтительный способ:

**Создавай пакет с помощью официальных механизмов Anki или совместимой библиотеки, например genanki.**

Если используется `genanki` или другой совместимый механизм экспорта:

1. Создай модель заметок через штатный API библиотеки.
2. Создай колоду с уникальным идентификатором.
3. Добавляй заметки и карточки только через предусмотренные библиотекой механизмы.
4. Создай пакет штатным экспортом непосредственно в `.apkg`.
5. Не удаляй, не сокращай и не упрощай автоматически созданные служебные структуры Anki.
6. Сохраняй полный набор обязательных и стандартных служебных свойств объектов колоды, модели, шаблонов и конфигурации, даже если часть из них не используется непосредственно карточками.
7. Не создавай минимальные JSON-объекты только из полей, которые кажутся необходимыми для текущей колоды.
8. Если внутренняя структура создаётся без `genanki`, она должна соответствовать реальной структуре пакета, созданного совместимой версией Anki или проверенной библиотекой, включая обязательные служебные поля и значения по умолчанию.
9. Не предполагай, что корректный JSON синтаксически автоматически является корректным объектом Anki: структура каждого объекта должна соответствовать ожидаемой схеме Anki.
10. Если невозможно надёжно определить полный формат внутренних структур для выбранной версии пакета, используй штатную библиотеку или другой проверенный механизм экспорта вместо ручного формирования JSON.

Не собирай SQLite-базу Anki вручную, если нет объективной необходимости.

Не создавай служебные таблицы произвольно.

Не копируй неполную базу данных из предыдущей колоды.

Не редактируй внутренний JSON колод вручную.

Если ручное создание внутренних структур всё же необходимо, используй полную совместимую структуру объектов Anki, а не сокращённое представление.

Для каждого внутреннего JSON-объекта:

* проверяй наличие всех обязательных служебных свойств;
* сохраняй стандартные поля со значениями по умолчанию;
* проверяй ожидаемые типы данных каждого свойства;
* не заменяй массивы объектами, объекты массивами, числа строками и наоборот;
* не удаляй поля только потому, что их значение равно нулю, пустому массиву или пустой строке;
* проверяй структуру не только обычным JSON-декодером, но и на соответствие формату Anki выбранной версии.

Внутренние структуры `decks`, `models`, `dconf` и другие служебные JSON-объекты должны быть полностью совместимы друг с другом и с версией SQLite-схемы пакета.

Не используй минимальную самостоятельно придуманную схему объектов Anki.

Не заменяй полноценный экспорт простым ZIP-архивом с самостоятельно составленной базой данных.

### Совместимость с Anki

Для создания файла используй формат, поддерживаемый современной версией Anki.

Проверь, что:

* Внутренние JSON-структуры колод, моделей и конфигурации содержат полный набор обязательных служебных полей для выбранной версии формата Anki, имеют правильные типы значений и успешно соответствуют ожидаемой структуре Anki; одной синтаксической валидности JSON недостаточно.
* Служебная схема SQLite соответствует используемому формату.
* Присутствуют все необходимые таблицы.
* Идентификаторы записей корректны.
* Все заметки связаны с существующей моделью.
* Все карточки связаны с существующими заметками и колодой.
* Содержимое и версия базы согласованы с форматом пакета.

Не пытайся самостоятельно исправлять каждую ошибку импорта последовательным добавлением недостающих таблиц.

Если экспорт получился несовместимым, исправь способ генерации пакета и создай его заново.

# 12. Обязательная техническая проверка

После создания файла проведи следующие проверки.

### Проверка 1. Архив

Убедись, что `.apkg` является корректным ZIP-архивом.

Проверь наличие обязательных компонентов пакета.

Проверь, что архив не повреждён.

### Проверка 2. База данных

Проверь целостность SQLite.

Проверь корректность структуры, идентификаторов и связей.

Убедись, что служебные таблицы соответствуют версии формата, выбранной механизмом экспорта.

Проверь, что имена колод и моделей корректно декодируются.

Дополнительно проверь внутренние JSON-структуры Anki:

* `decks`;
* `models`;
* `dconf`;
* другие JSON-поля служебных таблиц, если они используются выбранным форматом.

Для каждого объекта проверь:

1. JSON синтаксически корректен.
2. Корневой тип данных соответствует ожидаемому формату.
3. Все обязательные служебные поля присутствуют.
4. Типы значений соответствуют формату Anki.
5. Не отсутствуют стандартные поля только из-за того, что они имеют значения по умолчанию.
6. Ссылки между идентификаторами колод, моделей и карточек существуют.
7. Структура соответствует той версии формата Anki, для которой создаётся пакет.

Простого успешного вызова `json.loads()` или аналогичной функции недостаточно: синтаксически правильный JSON может оставаться несовместимым с Anki.

Если доступна эталонная структура, созданная `genanki` или самим Anki, сравни набор ключей и типы значений создаваемых объектов с ней перед финальной упаковкой.

### Проверка 3. Карточки

Убедись, что:

* Все заметки существуют.
* Каждая заметка генерирует ровно две карточки.
* Нет пустых лицевых сторон.
* Нет случайных дублей.
* Нет конфликтующих идентификаторов.
* Все необходимые поля заполнены.
* Оба шаблона правильно обращаются к существующим полям.

Проверь соответствие:

`Количество карточек = Количество заметок × 2`

### Проверка 4. Фуригана и HTML

Убедись, что HTML-разметка корректна.

Проверь, что фуригана видна над кандзи.

Убедись, что CSS применяется к обеим карточкам.

Проверь, что метки прилагательных отображаются отдельно.

### Проверка 5. Реальный импорт

**Если в рабочей среде доступен Anki или совместимый механизм импорта, обязательно выполни пробный импорт готового APKG.**

Проверь:

1. Импорт завершается без ошибок.
2. Колода появляется под правильным именем.
3. Количество карточек соответствует ожидаемому.
4. Оба направления карточек отображаются.
5. Фуригана отображается корректно.
6. Шаблоны и стили не повреждены.

Если полноценный пробный импорт технически недоступен, прямо сообщи об этом.

Не утверждай, что импорт проверен, если выполнялась только проверка архива или SQLite.

Успешная проверка целостности SQLite сама по себе не подтверждает совместимость с Anki.

Временные технические файлы допускаются только в процессе создания и проверки.

Не предоставляй пользователю промежуточные или заведомо повреждённые архивы.

Перед выдачей ссылки проверь, что итоговый файл действительно существует и доступен для скачивания.

# 15. Формат итогового ответа

После создания колоды сообщи:

**Урок:** {LESSON_NUMBER}

**Тема:** краткое описание основной темы урока.

**Заметки:** фактическое количество.

**Карточки:** фактическое количество.

**Файл:** `Japanese_Lesson_{LESSON_NUMBER}.apkg`

**Проверка:** укажи, какие технические проверки действительно выполнены и удалось ли провести пробный импорт в Anki.

Затем предоставь прямую ссылку на готовый файл.

Не утверждай, что колода полностью проверена, если какие-либо обязательные проверки не были выполнены.

# 16. Приоритет требований

При возникновении противоречий используй следующий порядок приоритетов:

1. Корректность японского языка и соответствие учебнику.
2. Возможность импорта файла в Anki.
3. Сохранение единого формата и оформления.
4. Сохранение единого стандарта именования.
5. Полнота словаря урока.
6. Качество примеров и объяснений.

Не жертвуй работоспособностью файла ради сохранения ошибочной внутренней структуры предыдущего архива.

Сохраняй визуальный дизайн эталона, но при необходимости пересоздавай техническую структуру корректным способом.

**Итоговая задача: готовая, корректная, самостоятельная Anki-колода, полностью соответствующая единому стандарту всех уроков Minna no Nihongo.**
